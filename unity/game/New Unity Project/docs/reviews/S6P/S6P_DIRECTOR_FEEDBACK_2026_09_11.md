## 1. 背包做成快捷键开关式

| 项 | 实现 |
|---|---|
| 热键 | `I` 切换 `SliceSession.BagOpen`（新增字段，默认 `true`，即启动时可立刻看到背包） |
| 面板内按钮 | 标题条右侧「关闭 I」；导航条新增「背包 I」（与「天赋 P」「制作 F8」同排） |
| `Esc` | 语义不变地同时关闭面板与背包（`s.Panel = None; s.BagOpen = false;`） |
| 底栏联动 | `SliceHud.CombatBarRects(dw, dh, bool bagOpen)`：背包关闭时底栏可用整幅宽度（原 2 参重载保留，等价于 `bagOpen = true`） |
| 绘画门 | `if (s.BagOpen) DrawDrawer(s); else { _drawer = default; _tray = default; }` —— 面板不画时不残留命中矩形（否则关闭后仍会拦截鼠标） |

**几何测试**（`DirectorFeedbackRegressionTests`，EditMode）：
- 背包关闭时底栏可用宽度**不减少**、底栏中心右移（严格宽度增长只在窄视口下断言——1920×1080 下底栏已顶到标称宽 1028 被钳住，不能强行断言变宽）。
- 关/开两态的面板与底栏矩形不重叠（面板贴右、底栏在剩余宽度内居中）。

**证据截图**：`docs/_dirshots/01_hud_bag_open.png`（开）、`02_tree_full_bag_closed.png`（关）。

## 2. 天赋树：点击不到 + 看不出一条线连着

导演原话：「我没法点击或者说人眼看他们不是通过线连接起来的」。两条症状都复现到了，根因不同：

### 2.1 「连不起来」的根因（实测数据）

| 根因 | 实测 | 后果 |
|---|---|---|
| 连线用**轨道公式反推端点** | 同轨道节点对 **1457 组中 0 组**落在该公式画出的圆上；节点到起点的距离恒为 335，而到所属 `group` 中心是 597–1209 | 画出来的弧线**全部悬空**，与节点无视觉接触 |
| 簇底衬用 canonical `group.x/y` | `group` 坐标与节点 `x/y` **不在同一坐标系**（起点 group 的 y=899.82，而该簇成员节点质心 y=6.82；最大偏移 18952） | 簇底衬落在离节点极远的位置，看起来像一堆无关的装饰 |
| 默认缩放 = 适配全树 | `FitZoom ≈ 0.044` | 2429 个节点压成约 2px 的点，即使有连线也「看不出一条线」 |

### 2.2 修法

| 修 | 内容 |
|---|---|
| 连线 | 改为**直接在真实节点坐标之间画直线**（canonical `links` 端点即节点自身坐标），线宽随缩放补偿 `max(1.7, 2.2*zoom+0.8)`，四种节点状态用不同明度区分 |
| 簇底衬 | 新增 `PoeTreeView.GroupRect/GroupCentre/GroupRadius`：中心=成员节点质心，半径=最远成员环半径 ×1.10 —— **几何从成员节点派生**，不再信 `group.x/y` |
| 默认视图 | `DefaultTreeZoom = 0.45`，并以起点节点为中心（`CentreOn(PoeTree.Get(StartNode), …)`），而不是缩到全树 |
| 可读性 | 节点按状态（已点/可点/不可点/专精）着色 + 图例文字 + 点击反馈 toast（成功/失败都给出可见回应，失败带原因） |

### 2.3 「点击不到」

点击本身是通的（加点/取消的点选链路未坏），但**可点节点极少**且视觉上无从判断，所以体感是「点不到」：

- 起点邻居 6 个，其中**可点 3 个**；从起点出发全树可达节点 = **2429 中的 14 个**。
- 全树「引擎可完整兑现」的节点有 367 个，其中 **353 个不可达**。
- 原因：WO-04A 的 fail-closed 支持门（阻塞节点整体拒绝）+ 与玩家实际掌握的解析能力相比，PoE 树上大多数节点的词条引擎兑现不了；这些节点又被当作「不可通行」，于是把整棵树切成了孤岛。

**这是本轮唯一需要裁决的产品级冲突，见 §5。**

**证据截图**：`docs/_dirshots/03_tree_zoom060.png`、`04_tree_zoom120.png`、`05_tree_default_view.png`。

## 3. 怪物移动/攻击没有动画

### 3.1 排查（先排除「接线没接」）

| 检查 | 结果 |
|---|---|
| 敌人 → 视觉映射 | 23/23 个木桩都拿到了 presenter，映射表命中 |
| 状态是否被请求 | presenter 收到 `Anim`（Idle/Run/Attack）、`HitFlash`、`AttackExecutions` |
| 预制体/Animator | 预制体存在、Animator 已启用、每套 6 条 clip |
| 骨骼是否真的动 | 修复后采样 `Bip01_R_UpperArm` 有位移（修复前 Run/Walk 段无位移） |

### 3.2 根因

`Troll_2_L_anims_split.fbx` 的 **Troll（蛮兵）系 5 条 clip 未勾选 Loop Time**：

```
Standby / Walk / Walk2 / Run / Attack_standby
```

非循环 clip 播到末帧即停 → Run/Walk 冻在最后一帧，外人看就是「移动没有动画」。
FireLion / Bruce / Gargoyle 三套本来就正确（已勾）。

### 3.3 修法与证据

- 通过 `ModelImporter.clipAnimations` 打开上述 5 条的 `loopTime`，再 `AssetDatabase.ImportAsset` 重导入（只改导入设置，不动美术资产本体）。
- 骨骼位移采样（编辑器中直接读 bone 的每帧位置差）：修复后 `Run` 段 `Bip01_R_UpperArm` 有连续位移。
- 回归测试：`DirectorFeedbackRegressionTests` 断言「敌人循环 clip 必须循环」。
- 修改文件：`Assets/Art/Enemies/TrollWarrior/Source/Troll_2_L_anims_split.fbx.meta`（唯一改动文件）。

## 5. 需要裁决的真值冲突：树可达性 vs WO-04A fail-closed 门

**冲突陈述**

- 一边：WO-04A（planner 已 ACCEPT）确立的唯一支持真相是 **fail-closed**——引擎无法完整兑现的节点整体拒绝，不得半消费。
  这条不变量是 04A 的全部价值所在，本轮**没有也不能**动它。
- 另一边：这条门把**未兑现**与**不可通行**绑在了一起，结果全树可达节点只有 **14/2429**（可点 3 个），
  导演看到的现象就是「点不动」。367 个「可完整兑现」的节点里 353 个被孤岛隔在外面。

**为什么我没有自行放宽**（按角色卡的 Source-of-Truth 冲突处置规则：记录漂移、不单方面改锁定设计）：

- 「不可兑现的节点是否仍可作为**通行节点**」是一个**设计决策**，不是 bug 修复：
  放行通行会改变树的可达性真值、可能改变加点序列的合法集合，属于 04A 不变量的语义边界。
- 没有这条放行，导演要的「点得到」与 04A 要的「不半消费」不可同时满足。

**候选方案（等裁决，不自选）**

| 方案 | 内容 | 代价 |
|---|---|---|
| A | **通行/生效分离**：不可兑现节点仍可点亮（占点、通行），但不产生任何 modifier | 需明确「点亮但不生效」的 UI 语义与审计口径；ProdSim 需重新基线（加点结果变） |
| B | **扩大可兑现域**：把更多 PoE 词条接进引擎（新增 Stat 轴），减少阻塞节点 | 直接移动 canonical 基线（`StatSnapshot` 按 StatId 全序哈希），且与 L1（无冰冷轴）同一类问题 |
| C | **收窄设计**：承认本阶段是「孤岛式演示」，在 UI 上把「未兑现」明确标成不可达并给出原因 | 不违 04A，但导演的「点得到」诉求只能部分满足 |

**建议**：A（语义最干净且与 PoE「点得动、词条可能没用」的真实体验一致），但**必须由导演/规划 AI 落章**，
因为它同时会触发 ProdSim 重新基线——这正是 WO-03 的职权范围，合流处理最省事。
